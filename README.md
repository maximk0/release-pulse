# Release Pulse

Release Pulse — рабочий веб-инструмент для асинхронной подготовки релиза. Он собирает сигналы из GitHub в один обзор: что движется, где есть проблемы и что сделать дальше. Это помогает разработчикам, тимлидам и менеджерам принимать решения с меньшим числом статусных созвонов.

Три экрана: короткая главная → подключение репозитория по URL → единый обзор с показателями, рисками, действиями и раскрываемыми источниками. Приложение только читает GitHub.

AI объясняет сигналы, выделяет подтверждённые риски и предлагает до трёх действий со ссылками. Локальный RAG ищет релевантные разделы README/docs и отбирает структурированные PR, issues и CI из всей загруженной выборки. Ответ проходит серверную проверку JSON, источников и достаточности контекста. Показатели и общий статус приложение вычисляет из GitHub-данных; AI не придумывает проценты готовности. Ошибка AI показывается отдельно, реальные данные остаются доступны.

AI должен давать конкретный разбор до трёх тем: работа по PR/issues, результаты CI и подготовка по релизной документации. Каждый блок связывает наблюдение с его значением и источниками, а до трёх действий описывают, что проверить или сделать и какой результат получить. Заголовок — только краткий вывод. Ответ без блоков, рисков и действий помечается `insufficient_data`; отсутствие выявленных рисков не подменяется придуманными проблемами. Успешный CI и наличие RELEASING.md не доказывают готовность выпуска: в MVP пока не задаются целевой релиз, срок и состав работ, а сравнение с предыдущей выборкой не передаётся AI.

## Запуск

Нужен установленный JDK 21 и интернет для зависимостей, GitHub и выбранного AI-провайдера. Gradle wrapper включён; Node/Yarn и Wasm-инструменты сборка скачивает сама.

1. Скопируйте `.env.example` в корневой `.env` и заполните нужные AI-переменные. Существующий `.env` не перезаписывайте; переменные процесса имеют приоритет.
2. Из корня репозитория выполните:

   ```sh
   ./gradlew :server:run
   ```

3. Откройте [http://127.0.0.1:8080](http://127.0.0.1:8080). Первая сборка дольше: компилируются Kotlin/Wasm и Skia. Остановка — Ctrl+C.

Backend сам раздаёт собранный UI; отдельный frontend-сервер не нужен. По умолчанию сервер доступен только локально, на порту 8080. Изменения `.env` требуют перезапуска. Без ключа выбранного AI-провайдера GitHub-обзор работает и показывает состояние «AI не настроен».

Текст обзора можно выделять. Кнопки копирования доступны для всего обзора, сообщения об ошибке, AI-выводов и раскрытых фрагментов. Даже после успешного ответа можно повторить только AI-анализ по сохранённым данным: это не обращается к GitHub. Экспорт обзора включает показатели, основания статуса, AI-выводы и ссылки. «Ссылки на источники» изначально свёрнуты; внутри есть фильтры и страницы по шесть ссылок с явным действием «Открыть в GitHub».

Экран данных называется «Пульс релиза». Логотип возвращает на главную, сохраняя текущую выборку и AI-ответ в памяти вкладки. На главной и в форме смены репозитория есть карточка с названием, временем выборки и кнопкой «Вернуться к пульсу репозитория»: возврат не вызывает GitHub или AI. Начатый анализ продолжается в фоне и не переключает экран после завершения. «Сменить репозиторий» открывает форму; предыдущие данные сохраняются до успешного подключения нового репозитория. «Отключиться» очищает сохранённый обзор и серверную сессию. При истёкшем подключении новые запросы переводят к форме с сохранённым URL и пустым полем токена, а предыдущую выборку всё ещё можно открыть для просмотра. Данные хранятся только в памяти: полная перезагрузка или закрытие вкладки их очищает и открывает главную; восстановление с диска не предусмотрено.

| Переменная | Назначение |
| --- | --- |
| AI-переменные | Указаны в `.env.example`; ключи используются только сервером |
| `GITHUB_TOKEN_READ_ONLY` | Необязательно; серверный read-only GitHub PAT из `.env` или окружения, используется при пустом поле токена |
| `PORT` | Необязательно, только окружение процесса; локальный порт сервера, по умолчанию 8080 |

AI-запрос выполняется на сервере и проходит общий JSON-контракт, RAG и проверку ссылок. Ключи не попадают в браузер, сообщения AI, ответы приложения или логи. При ошибке, отсутствии ключа или недостаточном контексте приложение показывает понятное состояние, а GitHub-данные остаются доступными. Изменения `.env` требуют перезапуска.

Ожидание AI не ограничено тайм-аутом приложения: сервер, браузер, живые тесты и проверочный скрипт ждут полного ответа, даже если генерация занимает несколько минут. Само истечение времени не запускает резервную попытку: она начинается после фактической ошибки или невалидного ответа. Если провайдер не завершит запрос, ожидание продолжится до разрыва соединения или остановки приложения. Отдельный тайм-аут чтения GitHub API — 20 секунд на запрос.

При сбое AI сервер делает только предусмотренную конфигурацией повторную попытку, после чего показывает безопасную категорию ошибки. Диагностика квоты и кредитов отделена от ошибок контекста и JSON. RAG помогает расходовать контекст экономнее, но не устраняет внешние ограничения квоты.

## GitHub

Для public repo достаточно `https://github.com/owner/repository`. Для private repo введите fine-grained Personal Access Token в защищённое поле. Выберите нужный репозиторий и read-only permissions: **Metadata**, **Contents**, **Pull requests**, **Actions**, **Issues**. Организация может требовать одобрения токена. Используются только GET-запросы GitHub REST API; права записи не нужны. Документация endpoints: [PR](https://docs.github.com/en/rest/pulls/pulls#list-pull-requests), [issues](https://docs.github.com/en/rest/issues/issues#list-repository-issues), [Actions](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-repository), [contents](https://docs.github.com/en/rest/repos/contents#get-repository-content).

Токен, введённый в интерфейсе, хранится только в памяти серверной сессии, максимум 8 часов, и удаляется при отключении. После перезапуска его нужно ввести снова. Можно заранее настроить `GITHUB_TOKEN_READ_ONLY` в корневом `.env` или окружении: сервер применит его при пустом поле, а введённый вручную токен получит приоритет. Значение серверного токена в браузер не возвращается. Переменные процесса имеют приоритет над `.env`; изменения требуют перезапуска.

Браузер получает только случайный HttpOnly/SameSite cookie. AI-ключи и GitHub-токены не входят в сообщения, ответы приложения или логи. Приложение не записывает токены на диск; `.env` с настройками создаёт пользователь и хранит вне Git. `.env`, настройки IDE и сборочные артефакты исключены из Git; `.env.example` разрешён для добавления в Git и содержит только placeholders. Существующие настройки IDE сохранены на диске.

## Ограничения MVP

- Один репозиторий на сессию, до 64 сессий в памяти. Нет аккаунтов, базы данных, истории или автоматического обновления. Перезагрузка страницы возвращает на главную; используйте кнопку обновления внутри обзора.
- До 300 открытых PR и 300 записей Issues API (из последних исключаются PR). При достижении лимита числа обозначены как нижняя граница. Недоступные счётчики отображаются прочерком. Это несколько запросов к API; GitHub может ограничить public-запросы без токена.
- Actions — последние до 20 запусков **default branch**. Диаграмма показывает `число запусков с результатом / размер выборки`; отменённые, neutral и skipped входят в «Прочие». Это не покрытие тестами и не все PR checks.
- Полные списки загруженных PR/issues/CI представлены в источниках; для просмотра описания ограничены 900 символами, документов — 3500. Полные загруженные тексты сохраняются в памяти RAG-индекса. Код, diff и вложенные каталоги docs не загружаются. Ошибка чтения необязательных документов уменьшает контекст; фактический объём виден в обзоре.
- Материалы репозитория, включая private repo, передаются выбранному AI-провайдеру для анализа. Перед подключением private repo проверьте политику команды. Содержимое считается недоверенными данными; защита от prompt injection и проверка ссылок не гарантируют истинности AI-вывода.
- Нужен современный браузер с WasmGC. Kotlin/Wasm + Skia дают сравнительно большой первый пакет (около 12 МБ Wasm без сжатия). Для внешнего размещения отдельно потребуются JVM-сервер, HTTPS и эксплуатационная настройка; публичный хостинг в MVP не развёрнут.

## Статус и подтверждения

Правила применяются в указанном порядке; рядом со статусом UI показывает фактические сигналы и ссылки.

| Статус | Сигналы |
| --- | --- |
| `insufficient_data` | Часть PR/issues/Actions API недоступна, нет Actions или последний запуск старше 14 дней |
| `blocked` | Самый свежий запуск Actions default branch имеет `failure`, `timed_out`, `action_required` или `startup_failure` |
| `attention` | Ошибка в истории, активный/отменённый/неизвестный результат Actions либо draft PR с подтверждённой релизной обязательностью |
| `ready` | Остальные случаи: в доступной выборке нет проблемных сигналов по этим правилам |

Обычный draft PR не влияет на статус и не служит самостоятельным основанием AI-риска. Подтверждение обязательности: явная метка `release-required`, `required-for-release`, `release-blocker`, `release:required` либо незакрытый пункт Markdown-checklist со ссылкой на PR в релизном разделе/файле. Такой draft даёт `attention`, а не сам по себе `blocked`. Открытые issues автоматически блокерами не считаются. Статус оценивает доступные сигналы, а не разрешает релиз; процента готовности нет.

Оценка AI дополнительно становится `insufficient_data`, если в извлечённом контексте нет содержательных критериев релиза или свежего CI, контекст пуст либо API частично недоступен. Консервативная проверка MVP требует фрагмент не короче 80 символов из раздела/файла с release/releasing/acceptance/checklist/релиз/критерии/приёмка и переданный CI с датой за последние 14 дней. Причина серверной проверки показана в ограничениях AI. JSON со ссылкой вне фактически переданного списка отклоняется целиком. Неподтверждённые риски и действия про draft PR исключаются отдельными карточками, остальные выводы сохраняются с меткой `insufficient_data` и заметкой о числе исключённых карточек. Для сохранения релизного риска по draft PR должно быть процитировано подтверждение его обязательности. Одинаковые правила применяются ко всем AI-запросам. Это узкая проверка правила про draft, а не проверка истинности всех AI-выводов.

## Локальный RAG

README, до 6 Markdown-файлов верхнего уровня `docs/` и до 2 корневых release/checklist/acceptance-файлов (каждый до 100 КБ) индексируются целиком в памяти сессии. По возможности они читаются на commit SHA default branch. Документы разбиваются по Markdown-заголовкам, длинные разделы — на фрагменты до 1100 символов с перекрытием; метаданные: `source`, `section`, `commit_sha`, `chunk_id`, строки. Отсутствие SHA явно отмечается.

Если список корневых файлов не дал два доступных релизных документа, дополнительно проверяются стандартные `RELEASING.md` и `RELEASE.md`; ранее проверенные пути не запрашиваются повторно. Ошибки чтения, HTTP-коды и пропуск слишком большого файла показываются в ограничениях выборки. Отсутствие необязательного стандартного файла (404) ошибкой не считается.

PR, issues и CI — отдельные структурированные записи с ID, датой, состоянием и URL. Три тематических запроса ищут сбои CI, PR/review и критерии релиза/блокеры. BM25-поиск объединяет результаты по ID, убирает дубли и переранжирует с учётом подтверждённой релизной обязательности и CI-ошибок. При наличии и достаточном бюджете в контекст сначала включаются последний CI и наиболее релевантный содержательный релизный фрагмент; справочные документы и история ошибок не вытесняют их. Сохраняется документальное подтверждение выбранного релизного PR. В AI-запрос уходит до 18 записей/чанков с суммарным текстом до 12 000 символов, плюс метаданные и рассчитанные кодом показатели. Выбранные фрагменты можно раскрыть в UI. Наличие инструкции выпуска само по себе не доказывает готовность конкретного релиза.

Отдельная векторная база и embeddings API для MVP не требуются. Это лексический поиск с английскими и русскими терминами; он может пропускать синонимы и не гарантирует полноту всех выводов. Полный корпус не передаётся одним AI-запросом целиком и не записывается на диск. Обновление GitHub-выборки перестраивает индекс, отключение удаляет сессию вместе с индексом.

## Проверки и демонстрация

```sh
./gradlew :server:test :server:installDist
```

Создаёт production-сборку Wasm UI и устанавливаемый сервер в `server/build/install/server/`. Автономные проверки покрывают JSON-контракт, источники, статусы, сессии, секреты, RAG, GitHub-загрузку и сборку. Они не обращаются к внешним AI-сервисам. Отдельные интеграционные проверки требуют явного запуска и расходуют внешние квоты; их результаты не являются гарантией качества анализа любого репозитория.

С запущенным сервером и Node.js 18+ можно повторить интеграционную проверку на реальном public repo:

```sh
node scripts/smoke.mjs
node scripts/smoke.mjs --ai
node scripts/smoke.mjs --ai --refresh
```

Варианты с `--ai` дополнительно вызывают настроенный AI-сервис; `--refresh` проверяет обновление и перестроение RAG. Скрипт не читает и не выводит credentials. Повторные проверки расходуют квоты внешних API.

Демо: на главной нажмите «Подключить GitHub», выберите пример `ktorio/ktor`, оставьте токен пустым. После проверки подтвердите распознанный репозиторий и откройте обзор. Сверьте счётчики и время выборки, дождитесь AI-карточек или понятной ошибки провайдера. Раскройте источники и перейдите к PR/Actions/issue, на который ссылается вывод. Проверьте ручное обновление. Недоступный репозиторий без токена должен дать ошибку доступа.

## Структура и стек

- `composeApp/` — три экрана Compose Multiplatform Web, target `wasmJs`.
- `server/` — Ktor, GitHub, AI-сервис, сессии в памяти и серверная валидация AI.
- `shared/` — Kotlin Serialization DTO для JVM и Wasm.
- `agent/` — исходный brief, правила и системный промпт; текст промпта включается в серверный ресурс при сборке.

Версии: Kotlin 2.4.21, Compose Multiplatform 1.12.2, Ktor 3.6.0, Gradle 9.7.0; JVM toolchain 21. Перед выбором сверены официальные [инструкции Kotlin/Wasm](https://kotlinlang.org/docs/wasm-get-started.html), [совместимость Compose](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html), [Kotlin/Gradle](https://kotlinlang.org/docs/multiplatform/multiplatform-compatibility-guide.html) и [Ktor](https://ktor.io/docs/releases.html).
